# Brand Identity System

> Canonical skill definition. Adapters in `adapters/` are thin wrappers over
> this file — they may not change purpose, procedure, outputs, quality gates
> or stop conditions. See `/PORTABILITY.md` and `/shared/adapters/README.md`.

## Identity
- **ID:** `brand-identity-system`
- **Category:** brand
- **Version:** `1.0.0`
- **Purpose:** Turn an approved visual direction into an operational
  identity system — logo usage rules, color tokens with exact values and
  usage rules, a type scale/tokens, spacing/grid rules, and iconography/
  imagery rules — concrete enough that a designer or a design-token file
  can be built directly from it, with no invented values.

## Trigger
Use this skill when:
- `BRAND_STRATEGY.md` is locked and `APPROVED_VISUAL_DIRECTION.md` exists
  and is the *selected* direction (not a territory still being compared).
- Identity rules (logo, color, type, grid, iconography, tokens) are needed
  before a brand book, design-token file, or component library can be
  built.

## Non-trigger
Do not use this skill for:
- Inventing brand strategy — that is `brand-strategy`, upstream.
- Generating or comparing creative territories, or producing
  `APPROVED_VISUAL_DIRECTION.md` itself — that is `brand-visual-direction`,
  upstream of this skill.
- Random logo ideation with no direction to systematize.
- Assembling the narrative brand book document — that is
  `brand-book-builder`, which consumes this skill's output.
- Building individual campaign assets or a content calendar — that is
  `creative-brief-generator` / `brand-content-system`.

## Context policy
- **REQUIRED_CONTEXT:** `BRAND_STRATEGY.md`, `APPROVED_VISUAL_DIRECTION.md`.
- **OPTIONAL_CONTEXT:** `VISUAL_ANTI_PATTERNS.md`, `GENERATION_LANGUAGE.md`
  (both from `brand-visual-direction`), `VERBAL_IDENTITY.md` (from
  `brand-verbal-identity`, for cross-referencing voice/tone against visual
  tone only — this skill does not write verbal rules), existing logo/font
  assets, font licensing constraints, the list of production channels in
  scope, prior `IDENTITY_SYSTEM.md`/`DESIGN_TOKENS.json` (for `mode: UPDATE`).
- **DO_NOT_LOAD_BY_DEFAULT:** the full brand-discovery/brand-strategy
  working conversation; discarded/runner-up entries from
  `VISUAL_TERRITORIES.md` (only the *selected* direction is canon here —
  re-litigating rejected territories is `brand-visual-direction`'s job);
  unrelated brands' token sets or component libraries; raw type-foundry
  catalogs beyond the family already selected or licensed.

Prefer canonical artifacts over conversational memory (`/ARCHITECTURE.md`).

- `BRAND_STRATEGY.md` — positioning, promise, differentiation, audience.

  (if in scope) motion principles, each traced to strategy. If this file

## Procedure
Numbered, executable steps. Every rule and every token value must trace to
`APPROVED_VISUAL_DIRECTION.md` (directly, or via a derivation method in
`references/`) — never to an unexamined default.

1. **Define identity architecture.** From the direction's compositional
   principles and (if supplied) `GENERATION_LANGUAGE.md`, define: the
   primary mark, wordmark, and lockup(s) (horizontal/stacked, and which is
   default per context); monochrome and reversed/inverse versions; minimum
   clear space and minimum size, each derived from the mark's own geometry
   (never an arbitrary round number) per
   `references/clear-space-and-minimum-size-derivation.md`; and an explicit
   forbidden-alterations list (stretch, recolor outside the defined
   palette, rotate, add effects, place on a background below the required
   contrast). If no mark exists yet to derive geometry from, stop this step
   and record it as a blocking gap (see Stop conditions) rather than
   inventing placeholder clear-space/size numbers.

2. **Define color roles and contrast behavior.** Convert the direction's
   color logic *rule* (not a palette dump) into named functional roles:
   primary, secondary (if any), accent, a neutral ramp (minimum 5 steps),
   and semantic roles (success, warning, error, info). For every role:
   exact value (hex, plus HSL if useful for programmatic ramps), the usage
   rule inherited from the direction's color-logic rule, and every
   text-on-surface / UI-on-surface pairing this role is approved for, each
   with a *computed* WCAG contrast ratio (method in
   `references/contrast-verification-method.md`) checked against the
   applicable threshold (4.5:1 normal text, 3:1 large text ≥24px/18.66px-
   bold and UI components/graphical objects). A pairing that fails is
   either dropped from approved usage or kept only for the use it actually
   passes for (e.g. "accent-on-light approved for fills/graphics only, not
   text — fails 3:1"). Never assert "meets AA" without the computed number
   next to it.

3. **Define typography roles.** Name the primary typeface (and secondary,
   if the direction calls for two families) plus a concrete system-font
   fallback stack. Define a type scale as a named step sequence
   (`type.100`...`type.n`) built from one explicit base size and one
   explicit ratio (name the ratio, e.g. "1.25 / major third") — not an
   unlabeled list of sizes. For each step: px/rem size, line-height, and
   default weight. Assign hierarchy roles (display, h1–h6, body, lead,
   caption, label, UI/button text) to specific steps. State tracking/casing
   rules and what changes across contexts vs. what never does. State
   responsive behavior explicitly (fluid clamp formula, or named
   breakpoint steps) — a scale silent on responsive behavior is incomplete.

4. **Define grid, spacing, shape, imagery and iconography systems.** Define
   one spacing scale from a single base unit (name it, e.g. "4px base") as
   named steps (`space.1`...`space.n`) with px values — every margin/
   padding/gap rule elsewhere in the system must resolve to one of these
   steps, not an off-scale number. Define the layout grid (columns, gutter,
   margin) per breakpoint in scope. Define a corner-radius scale
   (`radius.sm/md/lg/full`) and border/stroke-width tokens, both set
   according to the direction's materiality axis (sharp/precise vs.
   soft/approachable — state which pole was used and why). Define imagery
   treatment rules (crop ratios, color treatment, subject/framing
   convention, what is deliberately absent) traced to the direction's
   imagery language. Define iconography rules (grid size, stroke width,
   corner style, fill-vs-outline default) consistent with the radius scale
   and stroke-width tokens already set — icon style must not silently
   contradict the shape system.

5. **Define motion principles and UI translation.** If the direction states
   motion principles, convert them into duration tokens
   (`motion.duration.fast/base/slow`, in ms) and an easing token (a named
   cubic-bezier), plus the trigger-logic rule (state-change-driven vs.
   decorative — inherited from the direction, not re-decided here) and a
   restraint rule (what motion never does). If the direction states motion
   is out of scope, write that explicitly in `IDENTITY_SYSTEM.md` — do not
   leave the section silently absent.

6. **Create application rules across surfaces.** Write `APPLICATION_RULES.md`
   covering at minimum five surfaces relevant to the brand's channels (from
   web, social, decks/documents, ads, and product/UI — narrow to what
   `constraints`/`known_context` names as in scope, but never fewer than
   five unless `constraints` explicitly limits the channel set, in which
   case record that limitation rather than silently under-covering). For
   each surface: which tokens/rules apply unchanged, what adapts (e.g.
   safe zones and crop ratios per social placement, deck margins and
   maximum type steps per slide, ad legal-line placement, product/UI
   component-level token usage), and one concrete example application.

7. **Define exceptions and forbidden combinations.** Carry forward
   `VISUAL_ANTI_PATTERNS.md` where supplied, and add system-specific
   forbidden combinations discovered while building steps 1–6: forbidden
   logo/background pairings (below-threshold contrast), forbidden type
   pairings, any contrast-failing color pairing from step 2 (state it here
   even if already noted there), and any request-driven exception that
   would violate a rule above — record the exception and its owner/reason
   explicitly rather than silently allowing it.

8. **Create machine-readable design tokens.** Consolidate every value with
   a defined name from steps 1–7 into `DESIGN_TOKENS.json`, following
   `references/design-token-naming-convention.md`
   (`category.role.variant[-scale]`, e.g. `color.brand.primary`,
   `color.semantic.error`, `space.4`, `radius.md`, `type.scale.500.fontSize`,
   `motion.duration.base`). Every token's value must be byte-identical to
   the value stated in `IDENTITY_SYSTEM.md`'s prose — this file is a
   restatement of already-decided values, not a place to introduce new
   ones.

9. **Run the consistency and scalability audit.** Before marking the run
   complete, verify all of the following and record the result in
   `RUN_RESULT.quality`:
   - Every token in `DESIGN_TOKENS.json` has a corresponding prose rule in
     `IDENTITY_SYSTEM.md`, and every prose value has a corresponding token
     — no orphans on either side.
   - Every contrast claim in `IDENTITY_SYSTEM.md` carries a computed ratio
     that actually meets its stated threshold (re-check step 2's numbers).
   - Logo minimum size and clear space are stated in both an absolute unit
     and the mark-relative unit they were derived from.
   - `APPLICATION_RULES.md` covers at least five surfaces (or states the
     explicit channel limitation from step 6).
   - Every grammar element in `APPROVED_VISUAL_DIRECTION.md` (mood, color
     logic, typography logic, imagery language, compositional principles,
     and motion principles if in scope) is represented by at least one
     operational rule in `IDENTITY_SYSTEM.md`. Flag — do not silently
     drop — any grammar element with no operational translation.
   Stop only once this audit passes with no unresolved item, or record the
   specific failing checks in `unresolved` and return `status: PARTIAL`.

### Checkpoints
For `DEEP` mode or multi-sub-brand scopes, checkpoint after step 2
(architecture + color roles locked, contrast-verified) and after step 6
(application rules drafted, before token consolidation and the audit).
Record which roles/steps/tokens are locked and their values, so a resumed
run does not re-derive already-decided values — it re-uses them and
continues to step 7.

## Outputs

### Required output artifacts
- `IDENTITY_SYSTEM.md` — the full narrative identity system: architecture,
  color roles with computed contrast, typography, grid/spacing/shape/
  imagery/iconography, motion, and exceptions — each element traced to
  `APPROVED_VISUAL_DIRECTION.md`.
- `DESIGN_TOKENS.json` — the machine-readable token set, values identical
  to `IDENTITY_SYSTEM.md`.
- `APPLICATION_RULES.md` — surface-by-surface application rules across at

## Handoffs
- → `brand-book-builder` — primary handoff: passes `IDENTITY_SYSTEM.md`,
  `DESIGN_TOKENS.json`, and `APPLICATION_RULES.md` as the operational
  identity canon, alongside `VERBAL_IDENTITY.md` from `brand-verbal-identity`
  (parallel upstream skill) so the brand book assembles visual + verbal
  canon together rather than re-deriving either.
- → `creative-brief-generator` — when a specific asset/campaign brief needs
  this system's tokens and application rules before the full brand book
  exists.
- → `brand-quality-auditor` — when an existing/in-flight asset needs to be
  checked against `IDENTITY_SYSTEM.md`, `DESIGN_TOKENS.json`, and
  `APPLICATION_RULES.md` rather than a new system being built.

## Failure modes
- **Invented values with no trace.** Detect: a hex/pt/ms/ratio value in
  `IDENTITY_SYSTEM.md` with no citation to a grammar element in
  `APPROVED_VISUAL_DIRECTION.md` and no derivation method in `references/`.
  Fix: derive it properly, or if the direction genuinely doesn't specify
  enough to derive it, stop and name the gap in `unresolved` — do not fill
  it with a plausible-looking default.
- **Tokens and prose diverge.** Detect: a value in `DESIGN_TOKENS.json`
  doesn't match its stated value in `IDENTITY_SYSTEM.md`. Fix: resolve to
  one source value and update both files before marking complete — this is
  a hard audit failure (step 9), not a stylistic nit.
- **Contrast asserted, not verified.** Detect: "meets AA"/"accessible"
  language with no computed ratio next to it. Fix: compute the ratio per
  `references/contrast-verification-method.md`; if it fails, either narrow
  the approved usage (e.g. large-text/UI-only) or change the paired value.
- **Arbitrary clear-space/minimum-size.** Detect: a clear-space or
  minimum-size value stated only in an absolute unit with no mark-relative
  derivation. Fix: derive per
  `references/clear-space-and-minimum-size-derivation.md`; if no mark
  geometry was supplied, this is a blocking gap, not a number to guess.
- **Hero-surface-only coverage.** Detect: `APPLICATION_RULES.md` only
  covers one or two surfaces (typically web only). Fix: complete the
  required five-surface minimum, or record the explicit channel limitation
  from `constraints` that justifies fewer.
- **Motion section silently dropped.** Detect: `IDENTITY_SYSTEM.md` is
  silent on motion where `APPROVED_VISUAL_DIRECTION.md` specifies motion
  principles. Fix: complete step 5, or state explicitly that motion is out
  of scope if the direction says so.
- **Vague direction forces invention.** Detect: one or more grammar
  elements in `APPROVED_VISUAL_DIRECTION.md` are too abstract to derive a
  concrete rule from even after applying the relevant `references/` method
  (e.g. "color logic: colors should feel premium" with no rule for
  when/how color is used). Fix: do not invent a palette to fill the gap —
  return `status: PARTIAL`, name exactly which grammar element is
  underspecified, and recommend the run return to `brand-visual-direction`
  to sharpen it before re-running this skill.

## Quality gates
Skill must satisfy `/QUALITY_GATES.md` skill-level gates 1–10, plus:
- Every rule in `IDENTITY_SYSTEM.md` is operational (a designer or a token
  file could be built from it directly), not descriptive prose.
- `APPLICATION_RULES.md` works across at least five surfaces (or an
  explicit, recorded channel limitation justifies fewer).
- Every value in `DESIGN_TOKENS.json` matches `IDENTITY_SYSTEM.md` exactly.
- Every approved text/UI color pairing carries a computed contrast ratio
  meeting its stated threshold; failing pairings are narrowed or dropped,
  never asserted as passing.
- Every documented exception/forbidden-combination has a stated reason.

## Stop conditions
- Normal completion: all three required artifacts produced, step 9's audit
  passes with no unresolved orphan/contrast/coverage/grammar-translation
  issue, `status: COMPLETE`.
- Blocked (insufficient input): `BRAND_STRATEGY.md` is missing/unlocked, or
  `APPROVED_VISUAL_DIRECTION.md` is missing or is a territory-comparison
  document rather than a single approved grammar → `status: BLOCKED`,
  state exactly which artifact/element is needed.
- Partial (underspecified direction): one or more grammar elements are too
  vague to derive concrete rules from, even via `references/` methods →
  `status: PARTIAL`, name the specific missing/vague elements in
  `unresolved` and recommend returning to `brand-visual-direction` — do not
  invent values to reach `COMPLETE`.
- Never continue past: an invented value with no trace, a token/prose
  mismatch, an unverified contrast claim, or presenting fewer than five
  covered surfaces as if the minimum were met.
