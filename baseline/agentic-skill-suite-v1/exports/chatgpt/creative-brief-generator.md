# Creative Brief Generator

> Canonical skill definition. Adapters in `adapters/` are thin wrappers over
> this file — they may not change purpose, procedure, outputs, quality gates
> or stop conditions. See `/PORTABILITY.md` and `/shared/adapters/README.md`.

## Identity
- **ID:** `creative-brief-generator`
- **Category:** brand
- **Version:** `1.0.0`
- **Purpose:** Translate brand canon plus a specific business objective into
  an execution-ready brief for one concrete deliverable (web, campaign,
  social, video, deck, packaging or generated media) — not a restatement of
  the brand book.

## Trigger
Use this skill when:
- A concrete creative deliverable is needed (a named asset, not "some
  content ideas") — e.g. "landing page hero", "Instagram Reel campaign",
  "executive deck for Series A", "packaging redesign for SKU X".
- Brand canon exists (at minimum a strategy + verbal identity; ideally a
  compiled `BRAND_BOOK.md`).
- The next step is a handoff to a production agent, designer, copywriter,
  video editor or generative pipeline that needs to work without further
  clarification from a human.

## Non-trigger
Do not use this skill for:
- Defining or revising brand strategy, positioning or voice — that is
  `brand-strategy` / `brand-verbal-identity`. This skill consumes locked
  strategy, it does not create it.
- Generic ideation with no objective ("give me some post ideas") — send that
  to `brand-content-system` to build a content system first, or ask the
  requester for a concrete deliverable and objective.
- Producing final assets (copy, layouts, renders) by default — this skill's
  output is the brief a producer works from, not the produced asset itself.
- QA of an already-produced asset against canon — that is
  `brand-quality-auditor`, which this skill hands off to.

## Context policy
- **REQUIRED_CONTEXT:** the deliverable objective (what's being made and
  why), and brand canon covering at least strategy + verbal identity for the
  relevant audience/offer. Visual canon is required additionally for any
  visual deliverable (landing page, social creative, packaging, deck).
- **OPTIONAL_CONTEXT:** channel, target audience segment, offer/CTA,
  hard constraints (budget, legal, deadline), reference examples, a content
  brief from `brand-content-system` (when this deliverable is one instance
  of a running content system), prior brief for this same deliverable
  (`mode: UPDATE`).
- **DO_NOT_LOAD_BY_DEFAULT:** the full `BRAND_BOOK.md` text — pull only the
  sections relevant to this deliverable's audience/channel/format (see
  `references/canon-to-mandatories.md`). Unrelated deliverables' briefs.
  Full upstream conversation history from brand strategy/discovery — use the
  locked canon artifacts, not the discussion that produced them.

Prefer canonical artifacts over conversational memory (`ARCHITECTURE.md`).

## Inputs

### Minimum inputs
- Brand canon (strategy + verbal identity minimum; + visual identity for
  visual deliverables).
- Deliverable objective: what is being made, for what business/communication
  goal.

### Optional inputs
- Channel
- Audience (segment, if narrower than canon's default)
- Offer
- CTA
- Constraints (budget, legal/compliance, technical, deadline)
- References (competitor work, inspiration, prior campaign performance)
- Deadline

### RUN_REQUEST envelope
```yaml
RUN_REQUEST:
  objective:            # e.g. "landing page hero for Q3 pricing launch"
  source_artifacts:      # canon files: BRAND_BOOK.md, or STRATEGY.md + VERBAL_IDENTITY.md [+ VISUAL_IDENTITY.md], + optional CONTENT_PILLARS.md / content brief
  known_context:         # deliverable: type, channel, audience, offer, cta, references
  constraints:            # budget / legal / technical / deadline
  desired_output:         # full_brief_set | specific_artifact
  mode: STANDARD           # QUICK (lightweight, single-format) | STANDARD (full brief set) | UPDATE (revise against feedback/audit)
  prior_run:               # path to prior CREATIVE_BRIEF.md set, if mode: UPDATE
```

## Procedure
1. **Confirm canon exists and covers this deliverable.** Check that the
   supplied canon includes strategy + verbal identity, and visual identity
   if the deliverable is visual. If canon is missing or too thin for the
   deliverable type (e.g. a packaging brief with no visual identity system
   supplied), **stop and go BLOCKED** — do not invent brand rules to fill
   the gap. Name exactly which canon artifact is missing.
2. **Lock the objective and success signal.** State the single business or
   communication objective this deliverable serves, and the concrete signal
   that would indicate success (a metric, a behavior, a decision it should
   trigger). If the request implies more than one objective, force a
   priority call rather than writing a brief that chases both.
3. **Extract only relevant canon.** Pull the strategy, voice and (if
   applicable) visual rules that actually govern this deliverable's
   audience/channel/format — using `references/canon-to-mandatories.md`.
   Never paste the whole brand book into the brief; every mandatory listed
   must be traceable to a specific canon section, cited by name.
4. **Check the request against canon for conflicts.** Before drafting
   anything, compare the requested message/tone/claim/offer against locked
   canon constraints (banned claims, tone boundaries, legal/compliance
   rules). If the request conflicts with a locked constraint, do **not**
   silently comply and do not silently drop the request — flag the conflict
   explicitly (see Failure modes) and either resolve it only if canon gives
   an unambiguous answer, or leave it as an open flag requiring a decision.
5. **Define audience, context and job of the asset.** Who encounters this,
   in what moment/channel, needing to do what next. Pull from canon's
   audience definition; narrow to the deliverable's specific context — do
   not restate the brand's general audience section verbatim.
6. **Define the single-minded message, support points and CTA.** One
   sentence a producer could put in a headline. Up to 3 support points, each
   traceable to canon (positioning, proof points, offer) or the supplied
   offer/CTA — never invented. If two candidate messages both seem valid,
   pick one and note the alternative was considered and rejected (with why),
   rather than briefing both.
7. **Define visual/verbal requirements and anti-patterns.** What the
   deliverable must do (voice markers, visual system rules for this format)
   and explicit anti-patterns (what would read as off-brand or generic for
   this specific deliverable — not a generic "avoid AI slop" line).
8. **Specify format/channel constraints and variants.** Concrete
   dimensions/durations/lengths/slide counts for the named deliverable and
   channel (see `references/deliverable-format-specs.md`), plus any required
   variants (aspect ratios, lengths, languages).
9. **Define mandatory assets/data/legal/compliance inputs.** Everything
   production needs that isn't creative judgment: logos/photography/data
   points/legal copy/approved claims — each with a source or owner, into
   `ASSET_REQUIREMENTS.md`.
10. **Write production acceptance criteria.** Criteria specific and
    checkable enough that `brand-quality-auditor` (or a human QA pass) can
    mark PASS/FIX without re-deriving intent — never "looks on-brand."
11. **Generate the handoff tailored to the execution medium.** Identify who
    /what will produce the asset (designer, copywriter, video editor,
    generative pipeline, external agency) and write `PRODUCTION_HANDOFF.md`
    to reference `CREATIVE_BRIEF.md` + `ASSET_REQUIREMENTS.md` rather than
    restating them, adding only medium-specific execution notes (file
    naming, delivery format, review checkpoint, recommended next skill).
12. **Stop** when a designer/copywriter could execute directly from the
    brief set with no further questions to the brand, and no conflicting
    message, unsupported claim, or unflagged canon conflict remains.

### Checkpoints
For `DEEP`/multi-deliverable runs (e.g. a campaign with 4+ format variants),
checkpoint after step 8 (message + format specs locked across all variants,
before per-variant asset/acceptance detail), recording which
variants/formats are done so a resumed run only completes the remainder.

## Outputs

### Required output artifacts
- `CREATIVE_BRIEF.md` — objective, audience, single-minded message + support
  points + CTA, brand mandatories (canon-cited), anti-patterns, format/
  channel specs, acceptance criteria, open flags.
- `ASSET_REQUIREMENTS.md` — every mandatory asset/data/legal/compliance
  input, with source/owner, mandatory-or-optional, and deadline.
- `PRODUCTION_HANDOFF.md` — execution-medium-specific handoff referencing
  the brief + asset requirements, review checkpoint, and recommended next
  skill.

### RUN_RESULT envelope
```yaml
RUN_RESULT:
  status:      # COMPLETE | PARTIAL | BLOCKED
  summary:
  artifacts: [CREATIVE_BRIEF.md, ASSET_REQUIREMENTS.md, PRODUCTION_HANDOFF.md]
  decisions:    # message/priority calls made this run, and why
  unresolved:   # open flags: canon conflicts, missing assets, ambiguous priority
  handoff:      # recommended next skill + why
  quality:      # gate results
```

### Output schema
See `schemas/output.schema.json` for the machine-checkable shape of the
artifact set / RUN_RESULT.

## Handoffs
- → `brand-quality-auditor` — primary handoff: pass `CREATIVE_BRIEF.md` +
  `ASSET_REQUIREMENTS.md` as the canon-derived acceptance criteria for
  auditing the produced asset once it exists.
- → `brand-content-system` — when the request turns out to be one instance
  of a recurring content need rather than a one-off deliverable (e.g. "brief
  me a Reel" turns into "we need a Reel every week") — hand back the
  objective/audience/message work already done so the content system isn't
  built from scratch.

## Failure modes
- **Briefing a deliverable with no real canon behind it.** Detect: canon
  supplied doesn't cover the deliverable's required layer (e.g. visual
  identity missing for a packaging brief, or no canon supplied at all).
  Fix: `status: BLOCKED`, name the exact missing canon artifact — never
  invent placeholder brand rules to produce a brief anyway.
- **Silently complying with a request that conflicts with locked canon.**
  Detect: the requested claim/tone/offer contradicts a stated brand
  constraint (banned claim, tone boundary, legal rule). Fix: do not draft
  around it silently — state the conflict explicitly in `CREATIVE_BRIEF.md`
  under Open Flags and in `RUN_RESULT.unresolved`; only resolve it yourself
  if canon is unambiguous about which wins (e.g. a hard legal constraint
  always overrides a stakeholder's stylistic ask).
- **Dumping the whole brand book into the brief.** Detect: `CREATIVE_BRIEF.md`
  mandatories aren't traceable to specific canon sections, or the brief
  reads as generic brand-101 rather than deliverable-specific. Fix: re-run
  step 3 against `references/canon-to-mandatories.md`; cut anything not
  load-bearing for this specific deliverable.
- **Two competing key messages both make it into the brief.** Detect: the
  brief lists more than one "main" message, or support points contradict
  each other. Fix: force a priority decision (step 6); log the rejected
  alternative in `decisions`, don't brief both.
- **Acceptance criteria too vague for QA.** Detect: criteria read as
  subjective ("feels premium") with no way to check pass/fail. Fix: rewrite
  each criterion as a checkable statement (a rule, a measurement, a
  presence/absence check) `brand-quality-auditor` can apply without asking
  the brand team what was meant.
- **Unsupported claims treated as fact.** Detect: a support point or claim
  in the brief has no canon or approved-offer source. Fix: cut the claim or
  mark it as needing stakeholder/legal approval before it ships — never
  state it as a given.

## Quality gates
Skill must satisfy `/QUALITY_GATES.md` skill-level gates 1–10, plus:
- Every brand mandatory in `CREATIVE_BRIEF.md` cites the canon section it
  came from.
- Exactly one key message and one CTA per deliverable (variants of the same
  message are fine; contradictory messages are not).
- Every acceptance criterion in `CREATIVE_BRIEF.md` is checkable by
  `brand-quality-auditor` without further clarification.
- No claim appears in the brief without a canon or approved-offer source.
- A detected canon conflict is visible in `RUN_RESULT.unresolved`, never
  silently resolved in the brief's favor.

## Stop conditions
- Normal completion: all three required artifacts produced, single resolved
  message, canon-traceable mandatories, QA-checkable acceptance criteria,
  `status: COMPLETE`.
- Blocked: supplied canon does not cover the deliverable's required layer
  (missing strategy/verbal/visual as applicable), or no canon supplied at
  all → `status: BLOCKED`, name exactly which canon artifact is needed.
- Blocked/partial: the request conflicts with a locked canon constraint and
  canon does not unambiguously resolve which wins → flag in
  `RUN_RESULT.unresolved`, do not ship a brief that silently picked a side.
- Never continue past producing a brief with two conflicting key messages,
  an unsupported claim stated as fact, or a canon conflict presented as
  resolved when it wasn't.

# ChatGPT adapter — Creative Brief Generator

No native multi-file skill primitive, so this ships as a portable
instruction wrapper.

## Invocation
Custom GPT / Project instructions field:
> "You are the Creative Brief Generator. Follow the procedure in the
> attached `SKILL.md` exactly. On each run, expect a RUN_REQUEST (objective,
> canon source artifacts, known_context, constraints, mode). Produce all
> three required artifacts (`CREATIVE_BRIEF.md`, `ASSET_REQUIREMENTS.md`,
> `PRODUCTION_HANDOFF.md`) as separate, clearly labeled sections. Go BLOCKED
> if canon doesn't cover the deliverable; never invent brand rules. If the
> request conflicts with a locked canon rule, flag it explicitly — never
> silently comply or silently drop it."

Attach `SKILL.md`, `templates/`, and `references/` as Custom GPT knowledge
files.

## File I/O
Canon source artifacts are attached as Project/Custom-GPT knowledge files or
pasted inline. Outputs are returned as labeled markdown sections in the
chat response; the user saves them as separate files for the next
`mode: UPDATE` run (re-attach `CREATIVE_BRIEF.md` etc. as knowledge for that
run, alongside the same canon or its updated version).

## Environment constraints
Custom GPT knowledge files are read-only context, not a live filesystem —
every `UPDATE` run needs the prior brief set (and current canon) re-attached
explicitly.

## Fallback
This entire adapter is the fallback: ChatGPT has no native "skill folder"
primitive, so `SKILL.md`'s procedure is reproduced as system instructions.
