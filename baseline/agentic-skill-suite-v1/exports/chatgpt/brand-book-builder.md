# Brand Book Builder

> Canonical skill definition. Adapters in `adapters/` are thin wrappers over
> this file — they may not change purpose, procedure, outputs, quality gates
> or stop conditions. See `/PORTABILITY.md` and `/shared/adapters/README.md`.

## Identity
- **ID:** `brand-book-builder`
- **Category:** brand
- **Version:** `1.0.0`
- **Purpose:** Compile already-validated verbal identity and visual/identity
  system canon into one coherent, usable brand manual — without reopening,
  re-deriving, or silently patching any upstream decision.

## Trigger
Use this skill when:
- Both `VERBAL_IDENTITY.md`-family artifacts (from `brand-verbal-identity`)
  and `IDENTITY_SYSTEM.md`-family artifacts (from `brand-identity-system`)
  exist for the same brand.
- A client-facing or operational brand book/manual is needed so designers,
  writers and agents can execute without re-reading upstream chats.
- The brand workflow has reached the point in `/WORKFLOW_MAP.md` where
  verbal and visual identity both feed into a single compiled artifact.

## Non-trigger
Do not use this skill for:
- Brand discovery, strategy, voice, or visual-system derivation — those are
  `brand-discovery`, `brand-strategy`, `brand-verbal-identity`, and
  `brand-visual-direction` / `brand-identity-system`. This skill compiles
  their outputs; it does not create brand decisions.
- "Fixing" a poor or thin upstream strategy/voice/visual system by inventing
  better rules while assembling the book. A weak upstream artifact is a
  `BLOCKED`/flagged condition here, never a silent improvement.
- Auditing existing production copy/design against canon — that is
  `brand-quality-auditor`.
- A project where only one of verbal or visual canon exists. Route back to
  the missing upstream skill first (see Failure modes — do not compile a
  half-brand book and call it complete).

## Context policy
- **REQUIRED_CONTEXT:** all three verbal artifacts
  (`VERBAL_IDENTITY.md`, `MESSAGE_HIERARCHY.md`, `VOICE_EXAMPLES.md`) and
  all three identity-system artifacts (`IDENTITY_SYSTEM.md`,
  `DESIGN_TOKENS.json`, `APPLICATION_RULES.md`).
- **OPTIONAL_CONTEXT:** `BRAND_STRATEGY.md` (useful to resolve which side is
  authoritative when verbal and visual canon disagree about positioning),
  intended book audience (internal team, external agency, client-facing),
  format constraints (print vs. web vs. slide deck), example assets/photos
  already produced.
- **DO_NOT_LOAD_BY_DEFAULT:** full conversation/chat history from any
  upstream skill's run; brand-discovery raw research; rejected/deprecated
  positioning directions (unless needed to explain why a current rule exists
  — pull only the specific deprecated item, not the whole discovery corpus).

Prefer canonical artifacts over conversational memory (`ARCHITECTURE.md`).

## Inputs

### Minimum inputs
- `VERBAL_IDENTITY.md`, `MESSAGE_HIERARCHY.md`, `VOICE_EXAMPLES.md` (from
  `brand-verbal-identity`).
- `IDENTITY_SYSTEM.md`, `DESIGN_TOKENS.json`, `APPLICATION_RULES.md` (from
  `brand-identity-system`).

### Optional inputs
- `BRAND_STRATEGY.md`
- Intended audience for the book (internal / agency / client-facing)
- Format constraints (page count target, print vs. digital, slide format)
- Existing example assets/photography to reference in application sections

### RUN_REQUEST envelope
```yaml
RUN_REQUEST:
  objective:            # e.g. "compile client-facing brand book" | "update book after visual system revision"
  source_artifacts:      # must include all 6 required canon artifacts; optionally BRAND_STRATEGY.md, assets
  known_context:         # intended audience, format constraints, if not derivable from source_artifacts
  constraints:           # e.g. "executive depth only", "print-ready, 20 pages max"
  desired_output:        # full_book | outline_only | asset_checklist_only
  mode: STANDARD          # QUICK | STANDARD | AUDIT | UPDATE (only modes this skill supports)
  prior_run:              # path to prior BRAND_BOOK.md / checkpoint, required when mode is UPDATE
```
`mode: QUICK` produces the executive-depth book only (see step 2). `mode:
AUDIT` runs steps 1 and the coherence check (step 6) without producing the
full book — use it to check whether canon is book-ready before committing to
a full compile.

## Procedure
Numbered, executable steps. Each step should be concrete enough that two
independent runs against the same six canon artifacts converge on materially
the same book structure and the same set of flagged gaps — not a
freshly-reinvented brand book each time.

1. **Validate upstream sufficiency (gate).** Confirm all 6 required artifacts
   are present and each contains its load-bearing content: `VERBAL_IDENTITY.md`
   has traced, DO/DON'T-paired principles; `MESSAGE_HIERARCHY.md` has a
   master message and pillars; `IDENTITY_SYSTEM.md` has color roles,
   typography roles, and application rules; `DESIGN_TOKENS.json` is
   structurally valid JSON matching the prose in `IDENTITY_SYSTEM.md`. If any
   required artifact is missing entirely, **stop and return `BLOCKED`**,
   naming exactly which artifact and which upstream skill produces it — do
   not draft placeholder content in its place. If an artifact exists but is
   materially thin (e.g. `VERBAL_IDENTITY.md` has principles with no
   DO/DON'T, or `IDENTITY_SYSTEM.md` has swatches with no defined roles),
   proceed but log it in `unresolved` and flag it in the book's governance
   section — thin canon compiled as-is, not silently strengthened here.
2. **Choose book depth.** Based on `desired_output`/`constraints`/audience,
   pick one: `executive` (essence, positioning, voice snapshot, visual
   snapshot, 1-page do/don't — for leadership sign-off), `operational` (full
   voice + visual rules, application guidance, no governance/versioning
   detail — for an in-house team), or `full` (everything, including
   governance, versioning, and asset checklist — for an external
   agency/client). Record the choice and why; a `QUICK` run always picks
   `executive`.
3. **Build the narrative sequence.** Assemble the book in this fixed order
   (see `references/brand-book-toc-structure.md` for the section-by-section
   breakdown at each depth level): essence (mission/positioning summary from
   `BRAND_STRATEGY.md` if supplied, else from `MESSAGE_HIERARCHY.md`'s master
   message) → strategy snapshot → voice (from `VERBAL_IDENTITY.md` +
   `MESSAGE_HIERARCHY.md`) → visual system (from `IDENTITY_SYSTEM.md` +
   `DESIGN_TOKENS.json`) → applications (from `APPLICATION_RULES.md` +
   `VOICE_EXAMPLES.md`, paired so a single application shows voice and visual
   together) → governance (versioning, ownership, exceptions, `full`/
   `operational` depth only).
4. **Deduplicate while preserving necessary rules.** Where the same rule
   appears in multiple source artifacts (e.g. a tone note in both
   `VERBAL_IDENTITY.md` and an application example in `VOICE_EXAMPLES.md`),
   state it once in the book and cross-reference, rather than repeating full
   rationale each time. Never deduplicate two rules that only look similar
   but govern different contexts (e.g. "crisis tone" vs. "support tone") —
   collapsing those loses operational precision.
5. **Insert DO/DON'T and application guidance.** For every application
   surface covered in `APPLICATION_RULES.md` (web, social, decks, documents,
   ads, product/UI, etc.), pair the visual rule with the matching voice
   DO/DON'T from `VOICE_EXAMPLES.md` for that same channel where one exists.
   Where `VOICE_EXAMPLES.md` has no example for a surface `APPLICATION_RULES.md`
   covers (or vice versa), do not invent one — log the gap in
   `BRAND_BOOK_ASSET_CHECKLIST.md` instead (see step 7).
6. **Run the verbal/visual coherence check (core gate).** Using
   `references/verbal-visual-coherence-checklist.md`, cross-check whether the
   voice and the visual system actually describe the same brand: does the
   audience/tone implied by `VERBAL_IDENTITY.md` match the audience/formality
   implied by `IDENTITY_SYSTEM.md`'s color/type choices; do
   `MESSAGE_HIERARCHY.md`'s pillars/differentiators show up anywhere in
   `IDENTITY_SYSTEM.md`'s application rules or vice versa; does either
   artifact reference a positioning, audience, or category claim the other
   contradicts or never acknowledges. **Any mismatch found here is recorded
   as a flagged coherence gap — it is never silently resolved by picking a
   side or softening one artifact's language to match the other.** This is
   the check that catches "verbal and visual were built for subtly different
   positioning."
7. **Create the asset checklist.** Produce `BRAND_BOOK_ASSET_CHECKLIST.md`
   listing every example/visual/copy sample the book references but the
   source artifacts don't actually supply (e.g. an application rule for
   "email signature" with no worked example anywhere), plus every coherence
   gap from step 6, each tagged with which upstream skill/artifact should
   resolve it.
8. **Separate immutable canon from optional inspiration.** Mark every rule
   pulled from `VERBAL_IDENTITY.md`/`IDENTITY_SYSTEM.md`/`DESIGN_TOKENS.json`
   as canon (must-follow); mark anything illustrative-only (a mood reference,
   an example that shows a *style* of application rather than a *rule*) as
   inspiration, clearly labeled so a reader doesn't treat a suggestion as a
   requirement.
9. **Run the usability test.** Ask: could a designer or writer who has never
   seen the upstream artifacts execute a real deliverable (a landing page, a
   support reply, a one-pager) using only `BRAND_BOOK.md`? If any section
   requires knowledge not present in the book (an implicit rule the compiler
   understood from context but didn't write down), add it before completing
   — do not rely on the reader having read the source chats.
10. **Stop without silently changing upstream canon.** Complete when
    `BRAND_BOOK.md`, `BRAND_BOOK_OUTLINE.md`, and
    `BRAND_BOOK_ASSET_CHECKLIST.md` are produced, the coherence check (step 6)
    has run, and every gap/thinness/mismatch found is visible in
    `unresolved` and the asset checklist — none quietly patched by inventing
    a new rule that isn't traceable to `VERBAL_IDENTITY.md`,
    `MESSAGE_HIERARCHY.md`, `IDENTITY_SYSTEM.md`, `DESIGN_TOKENS.json`, or
    `APPLICATION_RULES.md`.

### Checkpoints
For a `full`-depth `STANDARD` run, checkpoint after step 3 (narrative
sequence assembled, sections populated, before dedup/coherence passes) and
after step 6 (coherence check complete, all gaps identified, before
finalizing the asset checklist and running the usability test). A resumed
run re-reads the checkpointed section content and gap list rather than
re-parsing all 6 source artifacts from scratch, unless a source artifact
itself changed (`mode: UPDATE`).

## Outputs

### Required output artifacts
- `BRAND_BOOK.md` — the compiled brand manual at the chosen depth: essence,
  strategy snapshot, voice, visual system, paired applications, governance
  (depth-dependent), with canon vs. inspiration clearly marked.
- `BRAND_BOOK_OUTLINE.md` — the table of contents actually used for this
  run, with depth level and one-line rationale per section (why included/
  excluded at this depth).
- `BRAND_BOOK_ASSET_CHECKLIST.md` — every missing example/visual/copy sample
  the book references but can't show, plus every verbal/visual coherence gap
  from step 6, each tagged with the upstream skill/artifact that should
  resolve it.

### RUN_RESULT envelope
```yaml
RUN_RESULT:
  status:      # COMPLETE | PARTIAL | BLOCKED
  summary:
  artifacts:   # [BRAND_BOOK.md, BRAND_BOOK_OUTLINE.md, BRAND_BOOK_ASSET_CHECKLIST.md]
  decisions:   # e.g. depth chosen and why, dedup decisions
  unresolved:  # e.g. coherence gaps, thin upstream artifacts, missing examples
  handoff:
  quality:
```

## Handoffs
Pass canonical artifacts + decisions + unresolved items + constraints + a
recommended next skill — never "read the whole conversation."
- → `creative-brief-generator` — passes `BRAND_BOOK.md` as the single
  reference a brief author needs, instead of all 6 upstream artifacts
  separately (see `routing-graph.json`).
- → `brand-content-system` — passes `BRAND_BOOK.md` (voice + message
  hierarchy sections load-bearing) as the canon a content system builds
  against.
- → `brand-quality-auditor` — when `unresolved` contains coherence gaps or
  thin canon that should be resolved before the book is trusted as
  audit-grade canon, or when existing production work needs auditing against
  the compiled book.
- → `brand-verbal-identity` / `brand-identity-system` — when step 1's gate
  fails (a required artifact missing) or step 6 finds a coherence gap that
  only an upstream skill can actually resolve (this skill flags, it does not
  fix).

## Failure modes
Concrete ways this skill can go wrong, and what to do instead:
- **Inventing a rule to fill a compilation gap.** Detect: `BRAND_BOOK.md`
  contains a voice or visual rule with no traceable line in any of the 6
  source artifacts. Fix: remove it; log the gap in
  `BRAND_BOOK_ASSET_CHECKLIST.md` and route back to the owning upstream
  skill instead. This is the primary failure this skill exists to prevent.
- **Papering over a verbal/visual coherence gap.** Detect: step 6 finds a
  mismatch (e.g. `VERBAL_IDENTITY.md` targets a premium/quiet audience while
  `IDENTITY_SYSTEM.md`'s color/type system reads loud/budget) but
  `BRAND_BOOK.md` presents both sections without comment, or silently
  softens one side's language so the mismatch stops being visible. Fix: keep
  both sections as-is, add an explicit flagged note in the book's governance
  section and in `unresolved`; never silently edit either source's meaning
  to make them appear aligned.
- **Compiling a half-brand-book.** Detect: only verbal or only visual canon
  was supplied. Fix: `status: BLOCKED`, name the missing artifact(s) and
  their owning skill; do not produce a "voice-only" or "visual-only" book
  labeled as a complete brand book.
- **Re-deriving instead of compiling.** Detect: the run re-runs strategic
  reasoning (e.g. re-justifying *why* a color was chosen from category
  analysis) instead of restating the rule already locked in
  `IDENTITY_SYSTEM.md`. Fix: state the rule and its source; leave the
  "why it was chosen" reasoning to the upstream artifact, cite it, don't
  redo it.
- **Losing operational precision to deduplication.** Detect: two rules that
  govern genuinely different contexts were merged into one because they
  sounded similar. Fix: keep both, distinguish contexts explicitly (step 4).
- **Silently rewriting canon on `mode: UPDATE`.** Detect: an UPDATE run
  changes book sections with no corresponding change in the source
  artifacts. Fix: delta only what actually changed upstream; state what
  changed and cite the updated source artifact.

## Quality gates
Skill must satisfy `/QUALITY_GATES.md` skill-level gates 1–10, plus:
- Every rule in `BRAND_BOOK.md` traces to `VERBAL_IDENTITY.md`,
  `MESSAGE_HIERARCHY.md`, `VOICE_EXAMPLES.md`, `IDENTITY_SYSTEM.md`,
  `DESIGN_TOKENS.json`, or `APPLICATION_RULES.md` — none invented in
  compilation.
- No two sections of `BRAND_BOOK.md` state contradictory rules without an
  explicit flagged note (contradictions are surfaced, not hidden or
  auto-resolved).
- The verbal/visual coherence check (step 6) has actually run and its
  findings (pass or gaps found) are stated in `RUN_RESULT.unresolved`, not
  omitted because "nothing major" was found.
- `BRAND_BOOK_ASSET_CHECKLIST.md` lists every missing example the book
  references and every coherence gap — none dropped silently.
- The book passes the step 9 usability test — a reader unfamiliar with
  upstream chats can execute from it alone.

## Stop conditions
- Normal completion: all three required artifacts produced, coherence check
  (step 6) run with findings recorded, usability test (step 9) passed,
  `status: COMPLETE`.
- Blocked (insufficient input): one or more of the 6 required upstream
  artifacts is missing → `status: BLOCKED`, name exactly which artifact(s)
  and which upstream skill produces them; no placeholder book is produced.
- Partial: all 6 upstream artifacts exist but step 6 finds a coherence gap
  serious enough that a compiled book would misrepresent the brand as
  aligned (e.g. contradictory audience/positioning signals between verbal
  and visual canon) → `status: PARTIAL`, book is still produced with the
  gap flagged prominently in the book itself, `BRAND_BOOK_ASSET_CHECKLIST.md`,
  and `RUN_RESULT.unresolved`, with a handoff recommendation to the owning
  upstream skill(s).
- Never continue past: presenting a coherence gap as resolved, or publishing
  any rule in `BRAND_BOOK.md` that cannot be traced to one of the 6 source
  artifacts — that is the exact "inventing brand decisions to fill gaps"
  failure this skill exists to prevent, and it fails the skill's purpose
  even if the run otherwise "completes."

# ChatGPT adapter — Brand Book Builder

No native multi-file skill primitive, so this ships as a portable
instruction wrapper.

## Invocation
Custom GPT / Project instructions field:
> "You are the Brand Book Builder skill. Follow the procedure in the
> attached `SKILL.md` exactly. On each run, expect a RUN_REQUEST (objective,
> source artifacts including all 6 required canon artifacts, constraints,
> mode). First run the sufficiency gate (SKILL.md step 1) — if any of the 6
> is missing, return status BLOCKED and name exactly which one and its
> owning skill; do not draft a placeholder in its place. Then run the
> verbal/visual coherence check (step 6) and record every gap found in
> BRAND_BOOK_ASSET_CHECKLIST.md and RUN_RESULT.unresolved — never silently
> resolve a mismatch by editing either source's meaning to match the other.
> Produce all three required artifacts (BRAND_BOOK.md,
> BRAND_BOOK_OUTLINE.md, BRAND_BOOK_ASSET_CHECKLIST.md) as separate, clearly
> labeled sections. Every rule in the book must trace to one of the 6
> source artifacts — never invent a rule to fill a compilation gap."

Attach `SKILL.md`, `references/`, and `templates/` as Custom GPT knowledge
files.

## File I/O
The 6 required canon artifacts (and optional `BRAND_STRATEGY.md`) are
attached as Project/Custom-GPT knowledge files or pasted inline. Outputs are
returned as labeled markdown sections in the chat response; the user saves
them as separate files and re-attaches `BRAND_BOOK.md` plus the current
canon for the next `mode: UPDATE` run.

## Environment constraints
Custom GPT knowledge files are read-only context, not a live filesystem —
every `UPDATE` run needs the prior book and the current canon re-attached
explicitly.

## Fallback
This entire adapter is the fallback: ChatGPT has no native "skill folder"
primitive, so `SKILL.md`'s procedure is reproduced as system instructions.
